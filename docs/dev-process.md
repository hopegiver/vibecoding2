# 바이브코딩 개발 프로세스

## 개요

바이브코딩에서는 **개발 프로세스를 상황에 따라 선택**합니다. 정답은 하나가 아닙니다.

| 접근 방식 | 핵심 | 적합한 상황 |
|-----------|------|------------|
| **프론트엔드 우선** | 화면 먼저 → 백엔드 역설계 | 요구사항이 불확실하거나 자주 바뀔 때 |
| **설계 기반 동시 개발** | 설계 문서 → 프론트/백엔드 동시 | 요구사항이 명확하고 도메인을 잘 알 때 |

두 접근을 혼합할 수도 있습니다. 확실한 부분은 설계 기반으로 동시 개발하고, 불확실한 부분은 화면 먼저 만들어 확인하는 방식입니다.

---

## 접근 방식 선택 기준

### 프론트엔드 우선이 좋은 경우

- 고객이 "원하는 게 뭔지 정확히 모르겠다"고 할 때
- 화면을 보여줘야 피드백을 받을 수 있을 때
- 비슷한 프로젝트를 해본 적이 없을 때
- SI/SM 프로젝트에서 빠른 고객 확인이 필요할 때

### 설계 기반 동시 개발이 좋은 경우

- 요구사항이 문서로 명확히 정리되어 있을 때
- 이전에 비슷한 시스템을 만들어본 경험이 있을 때
- 데이터 모델과 비즈니스 로직이 복잡할 때
- 팀이 도메인을 충분히 이해하고 있을 때

### 현실적인 접근: 혼합

실무에서는 **완벽한 설계 문서를 미리 만드는 것이 거의 불가능**합니다. 뒤로 갈수록 수정이 생기기 마련입니다. 그래서 대부분의 프로젝트는 두 방식을 혼합합니다:

```
확실한 기능 → 설계 문서 작성 → 프론트/백엔드 동시 개발
불확실한 기능 → 화면 먼저 → 고객 확인 → 백엔드 역설계
```

---

## 방식 1: 설계 기반 동시 개발

요구사항이 명확할 때, 설계 문서를 기반으로 프론트엔드와 백엔드를 동시에 개발합니다.

### 프로세스

```
1. 요구사항 분석 → 2. 설계 문서 작성 (PRD, 데이터 모델, API 스펙)
→ 3. 프론트엔드 + 백엔드 동시 개발 → 4. 연동 → 5. 통합 테스트
```

### 1단계: 요구사항 분석 + 설계

요구사항을 정리하고, AI에게 설계 문서를 작성하게 합니다:

```
"다음 요구사항으로 기술 설계 문서를 작성해줘:

- 회원 관리 시스템 (가입, 로그인, 프로필, 권한)
- 게시판 (CRUD, 카테고리, 검색, 첨부파일)
- 관리자 대시보드 (통계, 회원 관리)

포함 항목:
1. 데이터 모델 (엔티티, 관계, 필드)
2. API 스펙 (엔드포인트, 요청/응답)
3. 화면 목록 및 흐름
4. 비즈니스 로직 (권한, 상태, 유효성)"
```

**산출물:**
- `DESIGN.md` — 데이터 모델, API 스펙, 화면 목록, 비즈니스 로직

### 2단계: 동시 개발

설계 문서를 기반으로 AI에게 프론트와 백엔드를 함께 요청합니다:

```
"DESIGN.md를 읽고 회원 관리 기능을 구현해줘.
프론트엔드(pages/)와 백엔드(server/api/, server/dao/) 모두 만들어줘."
```

또는 기능 단위로 나누어 요청합니다:

```
"DESIGN.md의 게시판 부분을 구현해줘. 화면과 API를 함께 만들어줘."
```

### 3단계: 연동 + 테스트

프론트와 백엔드가 동시에 만들어지므로 별도의 Mock 단계 없이 바로 연동됩니다.

### 장점과 한계

**장점:**
- Mock → 실제 API 전환 과정이 없어서 빠름
- 데이터 모델이 처음부터 정규화됨
- 복잡한 비즈니스 로직도 설계 시점에 반영 가능

**한계:**
- 설계가 틀리면 프론트/백엔드 모두 수정해야 함
- 고객 피드백이 늦어질 수 있음 (화면을 먼저 보여주지 못하므로)
- **완벽한 설계는 현실적으로 어려움** — 뒤로 갈수록 수정이 생김

---

## 방식 2: 프론트엔드 우선 개발

요구사항이 불확실할 때, 화면을 먼저 만들어 고객과 확인한 후 백엔드를 역설계합니다.

### 프로세스

Vue Zero 풀스택 프로젝트 기준으로 진행합니다.

```
1. 요구사항 분석 → 2. 화면 개발 (고객 참여) → 3. 데이터 분리
→ 4. 데이터 통합 → 5. API 스펙 → 6. 비즈니스 로직
→ 7. DB 설계 → 8. 백엔드 개발 → 9. 실제 연동 → 10. 통합 테스트
```

### 왜 화면을 먼저 만드는가?

- **고객 피드백이 너무 늦음**: 기존 방식은 화면이 나오기까지 4\~6주 이상 소요
- **DB부터 설계하면 화면 요구사항과 괴리** 발생
- **고객은 화면을 봐야 판단 가능**: 문서만으로는 정확한 요구사항을 전달하기 어려움

Vue Zero는 빌드가 없어서 AI가 `.vue` 파일을 만들면 즉시 화면을 확인할 수 있으므로, 이 프로세스에 최적입니다.

---

## 단계별 상세

### 1단계: 요구사항 분석

**화면 중심으로 요구사항을 정리**합니다.

```
"게시판 시스템을 만들어야 해.
필요한 화면 목록:
- 게시글 목록 (페이징, 검색)
- 게시글 상세 (댓글 포함)
- 게시글 작성/수정
- 관리자 대시보드

각 화면에 필요한 데이터와 기능을 정리해줘."
```

**산출물:**
- 화면 목록 및 화면별 기능 정의
- 사용자 역할 정의
- 화면 흐름도

> **주의:** "화면에 보이지 않는 요구사항"도 반드시 기록하세요. 인증/인가 정책, 알림, 배치 처리, 외부 연동 같은 항목은 화면 목록만으로는 누락되기 쉽습니다.

### 2단계: 화면 개발 (고객 참여)

**바이브코딩의 핵심 단계입니다.** 고객과 함께 모든 화면을 AI로 빠르게 만듭니다. Vue Zero에서는 `app/pages/`에 `.vue` 파일을 만들면 즉시 URL이 생기고 화면을 확인할 수 있습니다.

**AI에게 이렇게 요청하세요:**

```
"게시판 목록 페이지를 app/pages/board/index.vue에 만들어줘.

화면 구성:
- 상단: 검색바 (제목+내용, 카테고리 필터)
- 중앙: 게시글 테이블 (번호, 제목, 작성자, 날짜, 조회수)
- 하단: 페이지네이션 (10개씩)
- 우측 상단: 글쓰기 버튼

샘플 데이터 5건을 data()에 넣어서 화면이 바로 보이도록 해줘."
```

**고객 피드백도 즉시 반영:**

```
"목록에 카테고리 뱃지를 추가해줘. 공지는 빨간색, 안내는 파란색으로."
```

```
"검색바를 상단 고정으로 바꿔줘. 스크롤해도 항상 보이게."
```

**사용자의 역할 — 판단과 피드백:**

- 화면을 보면서 고객과 함께 "이게 맞는지" 판단
- 고객 피드백을 AI에게 전달하여 즉시 수정
- 고객 피드백 루프 관리 — 확정 기준을 사전 합의 (예: 2회 리뷰 후 확정)
- **샘플 데이터가 나중에 DB 설계의 기초가 된다**는 점을 AI에게 전달:

```
"샘플 데이터는 나중에 DB 설계에 활용할 거야.
작성자는 userId로 참조하고, 날짜 형식은 통일하고,
상태값이 있으면 가능한 상태를 모두 포함해줘."
```

> Hook이 설정되어 있으면 AI가 `.vue` 파일을 만들 때마다 `pages.json`이 자동 갱신됩니다. 수동 등록 불필요.

**산출물:**
- `app/pages/`에 완성된 모든 화면 + 고객 확인 완료된 UI/UX

### 3단계: 데이터 분리

모든 화면이 확정되면, `data()`에 하드코딩된 샘플 데이터를 API 호출로 전환합니다. Vue Zero는 풀스택이므로 Mock JSON 대신 **바로 Hono API로 분리**할 수도 있습니다.

**방법 A: Mock JSON으로 분리 (안전한 방식)**

```
"모든 페이지의 샘플 데이터를 app/mock/ 폴더에 JSON으로 분리해줘.
페이지에서는 fetch로 JSON을 불러오도록 수정해줘."
```

**방법 B: 바로 Hono API로 분리 (빠른 방식)**

```
"모든 페이지의 샘플 데이터를 server/api/에 Hono API로 만들어줘.
일단 하드코딩된 데이터를 반환하는 API로 만들고,
페이지에서는 /api/ 경로로 fetch하도록 수정해줘."
```

> 방법 B를 쓰면 3~5단계를 한 번에 처리할 수 있어 빠르지만, 데이터 구조가 아직 불안정하면 방법 A가 안전합니다.

**확인할 것:** 분리 후 화면이 이전과 동일하게 보이는지 확인

**산출물:** 데이터가 분리된 페이지 + API 또는 Mock JSON

### 4단계: 데이터 모델 통합

화면별로 분리된 데이터에는 같은 엔티티가 중복되어 있습니다. DB 설계 전에 통합합니다.

**AI에게 이렇게 요청하세요:**

```
"모든 페이지와 API의 데이터를 분석해서:
1. 모든 엔티티(사용자, 게시글, 카테고리 등)를 식별하고
2. 각 엔티티의 전체 필드를 통합하고
3. 엔티티 간 관계를 정리해서
DATA-MODEL.md로 작성해줘."
```

**산출물:** `DATA-MODEL.md` — 엔티티 목록, 필드 통합, 관계도

### 5단계: API 스펙 정의

**AI에게 이렇게 요청하세요:**

```
"프론트엔드 코드와 DATA-MODEL.md를 분석해서 API 스펙을 작성해줘.
server/api/ 기준으로 엔드포인트 목록, 요청/응답 형식, 인증 필요 여부를 포함해줘."
```

**사용자가 보완할 것 — 화면에 없는 API:**

```
"다음 시스템 API도 스펙에 추가해줘:
- 인증: 로그인, 로그아웃, 토큰 갱신
- 파일 업로드 (R2)
- 이메일 중복 체크
- 권한별 접근 제어"
```

**산출물:** `API-SPEC.md` — 엔드포인트, 요청/응답, 인증 요구사항

### 6단계: 비즈니스 로직 정의

화면만으로는 드러나지 않는 **백엔드 처리 규칙**을 정의합니다.

**이 단계가 사용자의 핵심 역할입니다.** AI는 코드를 생성할 수 있지만, 비즈니스 규칙은 사람만이 결정할 수 있습니다:

```
"비즈니스 로직 문서를 작성해줘. 내가 정한 규칙은 다음과 같아:

- 게시글 삭제: soft delete, 본인 또는 관리자만 가능, 댓글은 유지
- 게시글 수정: 본인만 가능, 작성 후 30일 이내만
- 첨부파일: 최대 3개, 파일당 10MB, jpg/png/pdf만 허용
- 권한: 비로그인은 조회만, 일반 사용자는 본인 글만 수정/삭제, 관리자는 전체 삭제 가능

이 규칙들을 기능별로 정리해서 BUSINESS-LOGIC.md로 저장해줘."
```

> 사용자가 결정해야 할 것: 권한, 삭제 방식, 제약 조건, 상태 전이
> AI에게 맡길 것: 문서 포맷, 정리, 누락 항목 제안

**산출물:** `BUSINESS-LOGIC.md` — 기능별 처리 규칙, 권한, 상태 전이

### 7단계: DB 설계

**AI에게 이렇게 요청하세요:**

```
"DATA-MODEL.md, API-SPEC.md, BUSINESS-LOGIC.md를 읽고
D1 데이터베이스 스키마를 설계해줘. 정규화하고 인덱스도 설정해줘.
schema.sql로 저장하고, wrangler.toml에 D1 바인딩도 추가해줘."
```

**AI에게 맥락을 함께 전달하세요:**

```
"기존 데이터는 화면용 평면 구조야.
그대로 테이블로 만들지 말고 정규화해줘."
```

**산출물:** `schema.sql` + `wrangler.toml` D1 설정

### 8단계: 백엔드 개발

모든 설계 문서가 갖춰진 상태에서 `server/api/`와 `server/dao/`에 실제 API를 구현합니다.

**AI에게 이렇게 요청하세요:**

```
"API-SPEC.md, BUSINESS-LOGIC.md, schema.sql을 읽고
게시판 CRUD API를 server/api/와 server/dao/에 구현해줘.
응답 형식은 기존 페이지에서 사용하던 데이터 형식과 동일하게 맞춰줘."
```

**"응답 형식을 기존과 동일하게"** — 이 한 마디가 핵심입니다. 프론트엔드의 fetch 경로만 바꾸면 되도록 만들어줍니다. 개발 후 AI에게 "기존 데이터와 실제 API 응답을 비교해서 다른 부분 알려줘"라고 요청하세요.

> Hook이 `server/api/*.js` 파일 생성을 감지하면 `_registry.js`가 자동 갱신됩니다.

**산출물:** `server/api/`, `server/dao/` + DB 스키마 적용

### 9단계: 실제 API 연동

페이지의 데이터 호출을 실제 `/api/` 엔드포인트로 교체합니다.

**AI에게 이렇게 요청하세요:**

```
"모든 페이지의 데이터 호출을 실제 /api/ 엔드포인트로 변경해줘.
로딩 상태, 에러 처리, 인증 만료(401) 처리, 빈 데이터 상태도 추가해줘."
```

**"에러 처리도 추가해줘"가 중요합니다.** 이전까지는 항상 성공이었기 때문에, 이 시점에 로딩 UI, 에러 메시지, 401 리다이렉트 등이 없으면 나중에 전부 빠져 있게 됩니다.

### 10단계: 통합 테스트

**AI에게 이렇게 요청하세요:**

```
"전체 기능을 시나리오별로 테스트해줘:
1. 목록 조회 → 페이징 → 검색
2. 글 작성 → 목록에 반영 확인
3. 글 수정 → 상세에 반영 확인
4. 글 삭제 → 목록에서 제거 확인
5. 비로그인 시 작성/수정/삭제 차단 확인
6. 에러 상황 (잘못된 입력, 권한 없음) 처리 확인
7. wrangler dev로 로컬 전체 동작 확인"
```
